# SM86 and RTX 3090 gates

Load this reference for compute capability 8.6, GA102, or RTX 3090 work. Treat architecture and board specifications as limits; measure the installed board, host, artifact, and workload.

## Identity layers

Keep four identities separate:

1. **CUDA architecture:** compute capability 8.6 and its programming limits.
2. **GPU implementation:** GA102 resources and cache organization.
3. **Board:** RTX 3090 memory, power, clocks, PCIe interface, and optional physical links.
4. **Instance:** negotiated links, topology, cooling, power limit, clocks, build, dispatch, and sustained behavior.

A fact at one layer does not prove a fact at the next.

## Pinned specification packet

NVIDIA's GA102 whitepaper and archived CUDA guides establish these values:

| Property | RTX 3090 / GA102 / SM86 specification |
| --- | ---: |
| Streaming multiprocessors | 82 |
| CUDA cores | 10,496 |
| Tensor Cores | 328 |
| Board memory | 24 GB GDDR6X |
| Theoretical board memory bandwidth | 936 GB/s |
| L2 cache | 6 MiB |
| Unified L1 data cache/shared-memory pool per SM | 128 KB |
| Maximum shared memory per SM | 100 KB |
| Maximum shared memory per block | 99 KB |
| Resident warps per SM | 48 |
| Resident blocks per SM | 16 |
| Resident threads per SM | 1,536 |
| 32-bit registers per SM | 64K |
| Registers per thread | 255 |
| FP32 cores per SM | 128 |
| Board interface | PCIe Gen 4 |

Shared-memory allocations above 48 KB per block require dynamic shared memory and explicit opt-in. SM80/A100 tile choices that require 132–164 KB shared-memory carveouts do not transfer to SM86.

The 936 GB/s value is a theoretical board specification. Sustained application traffic depends on memory clocks, access efficiency, thermals, power, and workload.

## SM86-native optimization paths

### `cp.async` staging

- **Available mechanism:** hardware-accelerated global-to-shared copies can overlap movement and computation, avoid an intermediate register, and optionally bypass L1.
- **Supported copy widths:** 4, 8, and 16 bytes.
- **Preferred alignment:** CUDA documents 128-byte alignment for best `memcpy_async` performance; the promised alignment and divisibility must be true.
- **Gate:** generated SASS and runtime dispatch use the intended path; the tile has independent computation that can hide movement.
- **Lose-condition:** waits, alignment fallback, shared-memory demand, or stage bookkeeping costs more than the hidden latency.
- **Correctness:** respect per-thread completion, shared-data barriers, stage lifetime, and warp entanglement after divergence. Reconverge before shared pipeline commits or arrivals when required.

### Multistage software pipelines

- **Available mechanism:** `cuda::pipeline`, barriers, CUTLASS SM80-family implementations, and compiler-generated software pipelining can stage future tiles.
- **Gate:** stage count fits the 100 KB per-SM and 99 KB per-block limits plus register budget; producer and consumer work overlap.
- **Lose-condition:** stages reduce useful residency, wait frequently, or remain underfilled.
- **Proof:** compare stage counts, inspect resources and SASS, measure waits and kernel time, then confirm the end-to-end result.

### Tensor Core paths

SM86 supports Ampere Tensor Core instruction families, including FP16, BF16, TF32, INT8, INT4, and binary inputs for documented shapes and accumulation types. Concrete software paths remain conditional:

- prove the library or kernel accepts the shape and datatype;
- prove the built artifact contains a compatible target;
- prove runtime dispatch selects the expected kernel;
- inspect `mma.sync` or other material instructions when the claim depends on them;
- validate numerical or task-level quality.

A broad `__CUDA_ARCH__ >= 800` guard establishes compilation eligibility for SM86, not a distinct GA102 schedule or good RTX 3090 performance.

## Newer-architecture boundary

SM86 does not provide Hopper or Blackwell realizations such as:

- Tensor Memory Accelerator;
- warp-group MMA;
- thread-block clusters;
- distributed shared memory;
- native FP8 or FP4 Tensor Core paths.

Transfer the **causal idea**, not the instruction sequence. For example:

| Newer implementation | Portable idea | SM86 candidate |
| --- | --- | --- |
| TMA pipeline | overlap structured movement with computation | explicit tiling plus `cp.async` and a software pipeline |
| WGMMA producer/consumer kernel | specialize roles and overlap stages | warp-level `mma.sync`, shared staging, and measured producer/consumer roles |
| cluster/distributed shared memory | reuse data across cooperating blocks | redesign reuse inside one block or through a different global-memory decomposition |
| FP8/FP4 compute | reduce arithmetic and traffic cost | supported FP16/BF16/TF32/INT8/INT4 path with explicit conversion and quality gates |

If the portable substitute cannot reproduce the required semantics or economics, mark the technique unavailable rather than simulating the name.

## Build and dispatch proof ladder

1. **Pin the environment:** GPU UUID, compute capability, driver, CUDA runtime/toolkit, compiler, framework, package, source commit, and launch configuration.
2. **Read the support gate:** architecture, datatype, head/tile shape, alignment, shared memory, and feature combination.
3. **Inspect packaging:** use build logs and `cuobjdump`/`nvdisasm` to identify cubin, PTX, fatbinary, and target coverage when available.
4. **Exercise the exact path:** complete a representative request or kernel invocation and capture dispatch evidence.
5. **Trace the system:** connect the selected kernel to the target phase with Nsight Systems or explicit correlation.
6. **Inspect the kernel:** collect hypothesis-specific Nsight Compute metrics and SASS.
7. **Run one-mechanism A/B:** compare against the supported baseline across relevant shapes.
8. **Report the user outcome:** correctness or quality, latency/throughput, memory, tails, power, and thermals.

Packaging does not prove dispatch. Dispatch does not prove importance. Kernel improvement does not prove system improvement.

## Instance packet

Collect these values from the target instead of copying them from a reference rig:

- PCIe current and maximum generation and width under relevant load;
- pairwise CUDA P2P capability, correctness, latency, and bandwidth;
- optional physical-link topology and measured behavior;
- NUMA and CPU affinity;
- BAR1 and IOMMU state when relevant to the proposed mechanism;
- sustained clocks, power, temperature, performance state, and throttle reasons;
- usable memory after runtime reservation;
- exact binary, build target, selected kernels, and fallbacks.

Use stable GPU UUID or PCI bus identity in durable records. GPU indices can change across boots.

## Architecture-specific lose-conditions

Reject or retune a candidate when:

- an SM80 tile exceeds SM86 shared-memory or residency limits;
- reducing registers raises occupancy but adds spills or instructions;
- a nominal Ampere path JITs or dispatches a fallback with different behavior;
- a low-precision format saves storage but lacks an efficient SM86 execution path;
- a newer-GPU benchmark depends on TMA, WGMMA, clusters, distributed shared memory, FP8, or FP4;
- gains disappear under sustained RTX 3090 power or thermal behavior;
- the board specification is used as evidence for the negotiated host topology.
