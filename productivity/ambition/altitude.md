# Altitude

A task is the user's best guess at how to reach an outcome. Altitude asks for the outcome. The request moves from "fix this crash" to "keep the app crash-free".

Altitude fits when a real end result sits behind the request. A good sign is that people would hold meetings about the work. For creative work, where the making is the point, say that Altitude does not fit and use another type.

## The ladder

Felix Rieseberg's example is a request for a quarterly business review deck. Each rung asks for more of the outcome, and each has its reason:

- **Rung 1, explain.** A review exists to say what changed, why, and what to do about it. "Tell me what changed this quarter, why, and what we should do about it."
- **Rung 2, decide.** A good meeting ends in decisions. "Work out which three decisions are most urgent in the face of everything you've learned, and start working on potential directions with for/against arguments."
- **Rung 3, redesign.** The deck dates from a time when people had to sift the data by hand. "The review exists so leadership catches problems early and moves money and people to the right places. Design a better way to do that than a quarterly deck, show from our own history that it would have caught things sooner, and run it beside the current one for a quarter."

## Questions

1. What happens next with this deliverable? Name the outcome it serves: the goal beyond the goal.
2. Why does the deliverable have this form? Name the limits on human time and attention that shaped it and that an agent does not share.
3. Which repeating work is this request one instance of, and what would it mean for that outcome to hold without a new request each time?
4. What access, data, and environments would an agent need to own that outcome? Sort them into what exists here and what is missing.
5. What, other than the user or the agent, would show the outcome holds: over time, and against this project's own history?

## Moves for the rewrite

- **Write the top rung.** State what the deliverable exists for, and ask for a better way to get that than the deliverable itself. Step down a rung only when question 5 finds nothing that could check the outcome: "go make money" is still too broad for most businesses. That ceiling rises with each model, so aim high.
- **Give all the material.** Ask for the work to start from everything reachable about the situation, so that the agent understands the whole of it. The numbers or template the plain request would update are the smallest part.
- **Missing access is setup.** List the missing access, data, and environments from question 4 at the top of the rewrite as things to set up; a missing decision goes with the open choices. The rung stays where it is and the setup goes first, because an agent owns an outcome only when it can observe it and verify its own fixes. For "keep the app crash-free", the setup was crash reports it can fetch, a map from app version to commit, and machines on each platform to reproduce on.
- **Prove it on history.** Ask for evidence that the new approach would have caught past problems sooner, and for a period where it runs beside the current one.
- **Take the user out of the loop.** Ask for a durable workflow in which the agent watches the outcome, acts when it slips, and verifies its own fix, so that the user stops sending task after task. Name the trigger and the schedule in the rewrite, so the user sees what will keep running before sending it.
